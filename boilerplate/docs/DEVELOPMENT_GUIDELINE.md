# 開発ガイドライン

最終更新: 2026-04-04

## 1. はじめに

本ガイドラインは、プロジェクトにおける開発プロセスを定義し、品質、一貫性、保守性を確保することを目的とする。

開発は、**設計フェーズ** と **実装フェーズ** の 2 つの主要な段階に分かれる。これらは明確に区別されるが、開発サイクルの中で相互に行き来する反復的な関係にある。

両フェーズを通じて、以下の 2 つの基本原則を遵守する。

1. **仕様の完全な明文化**
   - ロジック、設計・実装上の注意点、背景理由まで、暗黙の前提を排除して文書化する。
2. **シナリオに基づくテスト**
   - 実運用で起こりうる現実的なシナリオを定義し、そのシナリオに基づいてテストを設計する。

補足:
- ドキュメント体系、分類、昇格、命名、運用手順は `docs/DOCUMENTATION.md` を正本とする。
- version 更新の判断、更新対象、更新手順は `docs/VERSIONING.md` を正本とする。
- コーディング上の意味論的な実装規約は `docs/CODING_GUIDELINE.md` を正本とする。
- `docs/TECHNOLOGY/INDEX.md` で選択済みprofileを確認し、対象に関係するTechnology Profileを必ずあわせて確認する。

## 2. ドキュメント体系とトレーサビリティ

本プロジェクトは、最新版の単一ソースと参照資料・意思決定・履歴を分離し、変更の流れを明確に保つ。

- `docs/INDEX.md`
  - 入口。最新仕様、参照、決定、履歴、計画への導線
- `docs/SPEC/*`
  - ビジョン、アーキテクチャ、インターフェース、ユースケースなどの仕様
- `docs/ADR/*`
  - 重要な設計判断の記録
- `docs/REF/*`
  - 運用ガイド、比較、SOP、設計補足
- `docs/history/*`
  - 検討過程、旧案、比較履歴
- `docs/WORK/*`
  - タスクやマイルストーンに閉じる作業文書
- `docs/WORK_LINE_ROUTING.md`
  - 計画開発と運用中の後続作業を Epic / MNT / OPS / ADV へ振り分ける規則
- `docs/agent_sessions/*`
  - セッション記録
- `docs/VERSIONING.md`
  - version 管理のルール
- `CHANGELOG.md`
  - 利用者、運用者、開発者に影響する未リリース変更とリリース履歴
- `docs/TECHNOLOGY/*`
  - 選択済み技術のguideline、実証reference、プロジェクト固有の採否

詳細な配置規則は `docs/DOCUMENTATION.md` を参照する。

## 3. プロジェクト計画の運用

本プロジェクトでは、戦略と戦術を分離した 2 層の計画書で開発を推進する。

- `docs/ROADMAP.md`
  - 中長期的なフェーズ目標と方向性を定義する
- `docs/PLAN_PHASE_CURRENT.md`
  - 現在フェーズの具体的な作業、WBS、担当、進捗を管理する
  - 必要に応じて、そのフェーズにおけるセッション粒度の方針も管理する

### 3.1 計画のライフサイクル

1. 開発は常に `PLAN_PHASE_CURRENT.md` に従って進める
2. 計画上の完了条件が満たされると、そのフェーズは完了である
3. 完了した計画は `docs/history/` にアーカイブする
4. 次フェーズ用に新しい `PLAN_PHASE_CURRENT.md` を作成する

### 3.2 セッション運用方針

必要に応じて、`PLAN_PHASE_CURRENT.md` の中に「セッション運用方針」を設け、そのフェーズにおいてどの粒度で AI との会話セッションを区切ると実装精度が最適化されるかを明記する。

特に次のようなケースでは、セッション粒度を明示することを推奨する。

- 前提として共有すべき背景、仕様、制約が大きく切り替わる場合
- 期待する成果物の種類が変わる場合
  - 例: 要件整理から設計、設計から実装、実装から検証
- UI / Interaction の設計と実装を分離したい場合
- 重い WBS を複数セッションへ分割する場合
- 仕様整理と実装を意図的に分ける場合

### 3.3 WBS ナンバリング規約

`フェーズ番号.マイルストーン番号.タスク番号`

例:
- `1.2.01`

### 3.4 WBS タスクの完了判定

WBS タスクの `[x]` は、AI の作業実施が終わった時点ではなく、ユーザー確認と必要な受入確認が完了した時点で付与する。

- AI が WBS タスクの作業を開始する場合、ユーザー承認後、実作業に入る前に `PLAN_PHASE_CURRENT.md` の対象タスクを `[>]` に変更する
- AI が実装、文書更新、自己確認を終えた段階では、対象タスクは原則として `[>]` のまま維持する
- ユーザーのレビュー、E2E / 実機確認、受入判断が残っている場合は、進捗ログに「確認待ち」として記録する
- 実装を伴う変更で E2E / 実機確認が必要な場合は、Runbook と確認スクリプトの準備までを当該タスクの作業範囲に含める
- 修正が発生した場合は、実装、検証準備、ユーザー確認、最終レビューのサイクルを繰り返す
- `[x]` への変更、完了済み成果物としての記録、次回再開プロンプトの確定更新は、ユーザーがレビュー完了または受入完了を明示した後に行う

### 3.5 フェーズ移行プロセス

フェーズを終了し、次フェーズを開始する場合は、単に `PLAN_PHASE_CURRENT.md` を差し替えるのではなく、次の順で実施する。

1. 現行フェーズのクローズ
   - `PLAN_PHASE_CURRENT.md` の目標、IN / OUT スコープ、完了条件、進捗ログを確認する
   - 全 WBS の完了状態と、ユーザー受入、E2E / 実機確認、最終レビューの有無を確認する
   - 完了要件を満たしていない項目は、未完了、後続フェーズ送り、またはスコープ外として明示する
2. 成果物と見送り事項の棚卸し
   - `docs/WORK/<phase>.*`、`docs/WORK/inbox/`、関連 `SPEC / ADR / REF / Runbook / session` を確認する
   - `promote`、`retain-in-work`、`delete` のいずれかに分類する
   - `docs/WORK/inbox/` の `open` を確認し、次フェーズ計画へ反映するもの、後続フェーズへ送るもの、対応不要として閉じるもの、継続確認するものに分類する
   - 次フェーズ以降へ送る事項は、再検討タイミング、送り先、再検討観点を持つ台帳として残す
   - `docs/TECHNOLOGY/ADOPTION.md` の採否、例外、一次検証、feedback候補を確認する
3. 次フェーズ計画の作成
   - `ROADMAP.md` を更新し、完了フェーズ、現在フェーズ、将来フェーズの位置づけを合わせる
   - 完了した `PLAN_PHASE_CURRENT.md` を `docs/history/PLAN_PHASE_<phase>_<yyyymmdd>.md` として退避する
   - 新しい `PLAN_PHASE_CURRENT.md` に、目標、IN / OUT、マイルストーン、セッション運用方針、WBS、横断制約、完了条件、リスク、成果物、進捗ログを定義する
4. 反映漏れレビュー
   - 前フェーズの成果物、Runbook、未解決事項、次フェーズ引き継ぎ文書を、次フェーズ WBS と突き合わせる
   - 次フェーズで実施するもの、さらに後続フェーズへ送るもの、長期バックログへ置くものを再分類する
   - 発見した漏れは `PLAN_PHASE_CURRENT.md` または適切な `WORK` 文書へ反映する
5. プロジェクト横断ナレッジの抽出
   - `knowledge-feedback` skillを使い、他プロジェクトでも有効な成功、失敗、分岐条件、運用知識を確認する
   - 抽出した内容は、まず `kit_feedback_internal_yyyymmdd_<slug>.md` に記録する
   - kitへ渡す場合は、固有名詞と参照パスを除いた `kit_feedback_export_yyyymmdd_<neutral-slug>.md` を別に作る
   - export検査とユーザー確認を通過したexport版だけを移送し、他リポジトリへ自動送信しない
6. 完了フェーズのセッション整理
   - 正式完了したフェーズに属するsessionを特定し、移動前にrepository内の参照を確認する
   - 参照切れを起こさないことを確認して、設定済みのsession root配下にあるフェーズ別archiveへ移す
   - 現行フェーズ、フェーズ間作業、最新の再開プロンプトはactive session rootへ残す
   - session pathがimmutable referenceまたは監査対象の場合は移動せず、代替索引または適用除外理由を記録する
7. セッション情報の更新
   - `docs/agent_sessions/session_yyyymmdd_nn.md` にクローズ結果、計画更新、棚卸し、反映漏れレビューを記録する
   - `docs/agent_sessions/chat_resume_prompt.md` に、次に着手する WBS、前提文書、注意点を更新する

フェーズ移行時の `PLAN_PHASE_CURRENT.md` の「技術的詳細と制約」は、WBS ごとの詳細設計を網羅する場所ではない。フェーズ全体にまたがる前提、横断制約、後戻りが大きい判断を置き、WBS ごとの詳細設計、API contract、Runbook、判断材料は `docs/WORK/<phase>.<milestone>/` に分ける。

フェーズ移行作業が完了したと判断するには、少なくとも次を満たす必要がある。

- 現行フェーズのクローズ判定が文書化されている
- 完了済み計画が `docs/history/` に退避されている
- `ROADMAP.md` と `PLAN_PHASE_CURRENT.md` のフェーズ状態が一致している
- 次フェーズ WBS が、前フェーズ成果物から導かれる引き継ぎ事項を反映している
- 後続フェーズへ送った事項が、後で再検討できる台帳または同等の文書に残っている
- `docs/WORK/inbox/` の `open` が確認され、各 capture の扱いが判定されている
- Technology Profileの採否と例外が棚卸しされ、汎用知識の有無が確認されている
- 完了フェーズのsession archive、active rootの残存範囲、参照切れの有無が確認されている。または適用除外理由と代替索引が記録されている
- セッション記録と再開プロンプトが更新されている

### 3.6 作業中の気づきの捕捉

作業中に発見した思いつき、機能追加候補、仕様変更候補、バグ、考慮漏れ、疑問は、必要に応じて `docs/WORK/inbox/` に捕捉する。

`capture inbox` は、作業の本筋を止めずに気づきを失わないための一時保管場所である。捕捉した時点では、仕様変更、WBS 変更、実装変更として確定しない。

捕捉する気づきの種別は、次の 3 種に限定する。

- `idea`
  - 思いつき、改善案、将来やりたいこと
- `issue`
  - 課題、仕様変更候補、バグ、考慮漏れ、リスク
- `question`
  - 疑問、確認事項、判断待ち

棚卸しは、セッション終了ごとではなく、WBS マイルストーン切り替え時、WBS の大きな組み替え時、フェーズ終了と次フェーズ計画策定時に行う。ここでいう WBS マイルストーン切り替え時とは、例えば `1.1` の完了後に `1.2` を開始する前のような区切りであり、必要に応じて実施する。

棚卸しは、必ず仕様や実装へ反映することではない。次 WBS や次フェーズへ影響するものを見極め、`promoted`、`deferred`、`closed`、または継続確認として `triaged` に分類する。

### 3.7 WBSマイルストーンクローズ時の技術知識レビュー

WBSマイルストーンを完了して次へ進む際は、必要に応じて次を確認する。

- `docs/TECHNOLOGY/ADOPTION.md` に追加すべき採否、例外、一次検証、後続検討があるか
- 技術選定ADRから `CODING_GUIDELINE.md` または `DEVELOPMENT_GUIDELINE.md` へ昇格すべき規律があるか
- 他プロジェクトでも有効な成功、失敗、分岐条件、運用知識があるか
- 汎用知識がある場合、`knowledge-feedback` skillでfeedback文書を作成するか

通常のセッションクローズごとには実施せず、WBSマイルストーンまたはフェーズの区切りで行う。

### 3.8 計画開発と運用作業の並行

最初の運用可能なリリース、共有環境へのデプロイ、または実利用開始以降は、現在フェーズのEpicと、リリース済み部分に対するMNT・OPSが並行しうる。作業線の判別と記録は `docs/WORK_LINE_ROUTING.md` を正本とする。

- 現在フェーズの計画開発はEpicとしてWBSで管理する
- リリース済み・運用中のbaselineへの修正はMNTとして管理する
- 障害やアラートの調査はOPSとして管理し、恒久修正はMNTへリンクする
- MNTでも新しい能力、重要な設計変更、複数マイルストーンの計画が必要になればEpic化を検討する
- MNTの実装にも、関連仕様、テスト、受入、migration、rollback、versioningの規則を適用する

## 4. 設計ガイドライン

**目的:** 「何を」「なぜ」作るのかを定義し、その振る舞いを予測可能にすること。

### 4.1 仕様の明文化

- 要件やアイデアは `docs/SPEC/` に落とし込む
- 大きな設計判断は `docs/ADR/` に記録する
- 暗黙知を排除し、第三者が読んでも誤解しない粒度で記述する
- UI / Interaction を持つプロジェクトでは、画面や操作導線も設計対象として扱う
- Web GUI を持つプロジェクトでは、早期フェーズにデザインモックまたは仮実装を行い、主要導線、レイアウト、デザインテーマの認識を合わせる
- 外部公開または外部連携されるエンドポイントを持つプロジェクトでは、API / Webhook / Callback / Request URL などの FQDN と環境別構成を設計対象に含める
- 技術選定ADRを確定した場合は、コードを書くたびに従うルールを `CODING_GUIDELINE.md`、開発・検証・deployのプロセス規律を本書へ昇格し、背景と比較はADRに残す
- ガイドラインへの昇格要否の確認までを、技術選定WBSの完了条件に含める

### 4.2 設計におけるテスト

- `SPEC` のユースケースや受入条件を基にテストシナリオを設計する
- 正常系だけでなく、異常系、フォールバック、性能、セキュリティも設計段階で洗い出す
- GUI / CLI / Chat UI を持つ場合は、状態、入力エラー、空状態、権限境界も設計対象に含める

### 4.3 設計フェーズの完了条件

- `SPEC` が更新されている
- 必要に応じて `ADR` が作成されている
- 主要ユースケースと異常系シナリオが文書化されている

## 5. 実装ガイドライン

**目的:** 設計で定義した仕様を、品質・保守性・安全性を保ちながら実装すること。

### 5.1 実装前確認

- 対象 WBS と完了条件を明確にする
- ユーザー承認後、作業開始前に対象 WBS を `[>]` に更新する
- 影響範囲を把握する
- 依存する `SPEC / ADR / REF` と、`docs/TECHNOLOGY/INDEX.md` で選択済みの関連profileを確認する
- version が関係する変更では `docs/VERSIONING.md` を確認する
- 利用者、運用者、開発者に意味のある変更では、`CHANGELOG.md` の `Unreleased` への追記要否を確認する
- 不足している仕様や判断事項を先に解消する

### 5.2 テストと検証

- 実装は設計で定義したシナリオに基づいて検証する
- 重要変更は、仕様とテストをセットで更新する
- 正常系、異常系、境界条件を確認する
- ユニットテストやローカル結合テストだけでは受入確認が完結しない実装変更では、E2E / 実機確認の Runbook を作成する
- 外部サービス、実行環境、複数アプリケーション、実機デバイス、ネットワーク、資格情報、ACL などを含む確認は、可能な限り確認スクリプト化する
- Runbook と確認結果は、対象範囲に応じて `WORK/x.y` または `REF_runbook-test_*` として管理する
- E2E / 実機確認が必要なタスクでは、Runbook と確認スクリプトの準備完了をもって AI 側の作業完了とし、人間による確認結果を受けるまでは WBS を `[x]` にしない

### 5.3 セキュリティと運用

- 入力検証、認証・認可、機密情報管理を考慮する
- 実行環境やプラットフォーム制約を無視した実装をしない
- 対象Technology Profileの `GUIDELINE.md`、`ADOPTION.md`、利用時点の公式一次情報を前提に実装する

### 5.4 ChangeLog の更新

- 機能追加、仕様変更、不具合修正、廃止、互換性影響を伴う変更では、実装と検証にあわせてルート `CHANGELOG.md` の `Unreleased` を更新する
- 記載対象と分類は `docs/VERSIONING.md` を正本とし、commit一覧や作業手順ではなく、変更の結果と影響を記載する
- versionを更新しない変更も、次回リリースで告知すべき内容なら `Unreleased` に残す
- リリース時はversion正本の更新と同じ変更で、`Unreleased` の内容を日付付きversion節へ移す

### 5.5 Git commit の実行と記録

#### 5.5.1 承認境界

- ファイル変更の承認は、Git commit の承認を兼ねない
- ユーザーが commit を明示的に依頼または許可した場合に限り、承認された範囲を commit してよい
- commit の承認は、push、amend、rebase、merge の承認を含まない
- commit の承認を求める場合は、対象ファイルと提案する commit message を事前に示す
- ユーザーの依頼に commit が明示的に含まれる場合は、同じ commit について重複して承認を求めない

#### 5.5.2 commit 前の確認

- `git status --short` と staged diff を確認する
- 承認範囲のファイルだけを明示的に stage し、無関係な変更を含めない
- `git diff --check` と `git diff --cached --check` を実行する
- staged diff から変更の目的、理由、主要な変更、確認結果を把握してから commit message を作成する

#### 5.5.3 commit message

- commit message の説明部分と本文は原則として日本語で記載する
- プロジェクトが Conventional Commits 等の形式を採用している場合は、`feat`、`fix`、`docs` 等の種別と scope はその形式に従い、変更の説明は日本語で記載する
- 件名には、ファイル操作ではなく変更の目的または結果を簡潔に記載する
- 「ファイルを更新」「修正」「変更」「WIP」など、履歴から変更内容を特定できない件名を使用しない
- 小さく自明な変更は件名だけでよい
- 小さく自明な変更を除き、本文に「変更理由」「変更内容」「確認内容」を記載し、関連する WBS / MNT / OPS / issue があれば「関連」に記載する

標準形は次のとおりとする。

```text
<type>(<scope>): <変更の目的または結果を日本語で記載>

変更理由:
- なぜこの変更が必要だったか

変更内容:
- 主要な変更内容

確認内容:
- 実施したテストや確認

関連:
- WBS 3.2.01
```

例:

```text
docs(git): コミットメッセージの品質要件を定義

変更理由:
- AIが作成したコミットの目的を履歴から判断しにくい場合があったため

変更内容:
- ファイル変更とコミットの承認境界を明確化
- コミットメッセージに目的、理由、確認内容を残す規則を追加

確認内容:
- 配布用AGENTSと開発ガイドラインの記載内容を確認
```

#### 5.5.4 commit 後の報告

- commit hash と commit message を報告する
- commit に含めた対象範囲を報告する
- push の有無を明示する
- 未 commit の変更が残っている場合は、その存在と対象を報告する

## 6. 新規アプリケーション開始プロセス

新しいアプリケーションまたはサービスを着想した場合、要求開発、技術検討、非機能要件整理、段階計画を行ってから実装へ進む。

### 6.1 標準フロー

1. 発想の記録
2. 要求とプロダクト定義
3. UI / Interaction 構想（必要な場合）
4. 技術候補と非機能要件の検討
5. Technology Profileの選定と追加
6. 開発成熟度とフェーズの定義
7. ロードマップ作成
8. 現在フェーズ計画化
9. WBS 分解
10. 実装着手判定

初期構想文書の役割は `docs/DOCUMENTATION.md` を参照し、対話的な要求整理には `project-bootstrap` skill を使用する。

### 6.2 開発成熟度

フェーズ番号と開発成熟度を同一視しない。各フェーズが次のどの段階を担うか明記する。

- 技術実現性検証
  - 採用技術と構成で中核処理を実現できるか確認する
- 構想・利用体験検証
  - 想定利用者が意図した価値や体験を得られるか確認する
- 初期実用提供
  - 実際の利用者が最低限継続利用できる状態を整える
- 本格提供・拡張
  - 信頼性、運用性、規模、機能を拡張する

PoC は技術実現性検証または構想・利用体験検証を目的とする検証活動であり、初期実用提供と同義ではない。PoC が複数フェーズに跨る場合は、各フェーズの検証範囲と PoC 全体の完了条件を明記する。

プロダクト価値が GUI や操作体験に依存する場合、API のみの実装では構想・利用体験検証の完了としない。主要利用者が価値を確認できる簡易 Interface を PoC に含める。

### 6.3 技術候補の検討

技術、プラットフォーム、外部サービスを選ぶ場合は、候補を比較し、利用者が判断できる材料を提示する。

- 実現可能性
- プラットフォーム制約
- セキュリティ上の境界
- 性能と拡張性
- 開発・運用負荷
- 無償利用範囲と将来コスト
- ベンダーロックインと変更難易度
- PoC や事前検証の必要性

AI は推奨案と理由を提示できるが、未確認の前提を補って技術構成を確定してはならない。

Technology Profileは `init-project.mjs` 実行時に未指定でもよい。WORK/0.1の対話で採用技術が確定した時点、または実装着手判定までに、`technology-profile-governance` skillを使って対応profileを追加する。未収録の技術は、公式一次情報と一般ガイドラインで扱い、profile追加候補として記録する。

### 6.4 非機能要件の初期整理

初期構想段階では、全非機能要件を詳細設計するのではなく、プロダクトの成否を左右する事項と、事前検証が必要な事項を特定する。

- セキュリティ
  - 守るべきデータ、権限、操作、認証・認可・監査境界
- 性能・負荷
  - 主要処理の目標、想定規模、ピーク、負荷試験や事前計測の要否
- コスト
  - 課金要素、無償利用範囲、有償化の閾値、月額上限、構成変更の判断基準
- 運用・可用性・復旧
  - 監視、ログ、通知、停止許容、復旧方法、運用担当

### 6.5 UI / Interaction と外部エンドポイント

UI / Interaction があるプロジェクトでは、初期構想段階で `docs/WORK/0.1/interaction_design.md` を使って方向性を整理する。
Web GUI があるプロジェクトでは、WBS 分解時にデザインモック / 仮実装のタスクを設けるか判断する。
外部公開または外部連携されるエンドポイントがあるプロジェクトでは、WBS 分解時に FQDN 設計のタスクを設けるか判断する。

### 6.6 実装着手判定

実装着手前に、少なくとも次を確認する。

- 解く課題、対象利用者、初期提供範囲が明確である
- 技術実現性検証、構想・利用体験検証、初期実用提供の位置付けが明確である
- クリティカルなセキュリティ、性能、コスト上の判断が整理されている
- 未決事項と事前検証タスクが WBS または適切な文書に反映されている
- 現在フェーズの完了条件と受入条件が明確である
- 採用済み技術に対応するprofileの追加要否が判断され、選択済みprofileの初期採否が `docs/TECHNOLOGY/ADOPTION.md` に記録されている

## 7. Technology Profileのライフサイクル

- profileはruntime、integration、storage、framework、toolingなど複数の技術要素を組み合わせて選択できる
- 選択済みprofileの索引は `docs/TECHNOLOGY/INDEX.md`、プロジェクト固有の採否と差異は `docs/TECHNOLOGY/ADOPTION.md` を正本とする
- 実装前に対象WBSと関係するprofileだけを読み、無関係なprofileを一律にコンテキストへ含めない
- limits、pricing、API、設定仕様など変動する事実は、利用時点の公式一次情報を優先する
- profileの共通文書をプロジェクト事情で直接変更せず、差異は `ADOPTION.md` に記録する
- ADR確定、E2E、production運用、障害対応で得た知識を `ADOPTION.md` へ継続反映する
- 他プロジェクトにも有効な知識は、マイルストーンまたはフェーズのクローズ時にknowledge feedbackとして抽出する
