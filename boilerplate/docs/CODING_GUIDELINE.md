# コーディングガイドライン

最終更新: <DATE>

本ドキュメントは、このプロジェクトにおけるコーディング上の実装規約を定義する正本である。  
書式や整形の詳細は formatter / linter に委ねつつ、ここでは意味論的な実装ルールを扱う。

## 1. 目的

- バグを生みやすい実装を避ける
- 暗黙挙動を減らし、デバッグしやすいコードにする
- 将来の変更や運用で破綻しにくいコードを書く
- パフォーマンスと保守性の両方を損なわない

## 2. 基本原則

- 挙動は明示する
- 不正な状態は早く失敗させる
- 暗黙の補完より、明示的な設定と検証を優先する
- 1つの関数、1つのモジュールの責務を増やしすぎない
- コードの短さより、意図の読みやすさを優先する

## 3. 設定値とデフォルト値

### 3.1 必須設定

- 必須設定は、未設定時にコード内で暗黙のデフォルト値を補わない
- 未設定、不正値、範囲外の設定は、明示的な設定エラーとして検出する
- 認証、権限、配送品質、外部送信先、削除動作、課金関連などの重要設定では、暗黙フォールバックを禁止する

### 3.2 任意設定

- デフォルト値を許可するのは、未指定でも安全で、挙動が利用者にとって予測可能な場合に限る
- デフォルト値を採用する場合は、仕様または設定ドキュメントに明記する
- デフォルト値を使う理由が説明できない場合は採用しない

### 3.3 fail-fast

- 「静かに補完して動く」より、「明示的に失敗する」を基本方針とする
- 起動時または実行時に設定不備を検知できるなら、早い段階で失敗させる

## 4. 複雑性の抑制

- 1つの関数で、複数の責務を同時に持たせない
- 条件分岐が深くなりすぎる場合は、前提検証、判定、処理を分ける
- 暗黙の共有状態より、明示的な引数と返り値を優先する
- 一時しのぎの分岐や特殊ケースを積み上げすぎない
- 同じ意味のロジックが複数箇所に現れたら共通化を検討する

## 5. エラーハンドリング

- 失敗しうる処理は、失敗を前提に書く
- 例外やエラーは握りつぶさない
- リトライ可能な失敗と、即座に中断すべき失敗を分ける
- 利用者向けのエラーと、運用者向けの診断情報を混同しない

## 6. データと状態

- 入力値は境界で検証する
- null / undefined / 空文字 / 0 の意味を混同しない
- 可変状態は最小限にする
- 時刻、乱数、外部 I/O に依存する処理は分離し、テストしやすくする

## 7. パフォーマンス

- 意味なく同じ計算や I/O を繰り返さない
- ループや再帰の中で高コスト処理を重ねない
- 不要な多重処理、重複取得、重複変換を避ける
- 先に正しさを確保しつつ、明らかなボトルネックは放置しない

## 8. ログと観測性

- 失敗時に追跡できる最小限の情報を残す
- 機密情報や過剰な payload をそのままログへ出さない
- 何が起きたか、なぜ失敗したかが分かる粒度で記録する

## 9. 依存関係

- 新しい依存を追加する理由を説明できるようにする
- 小さな便利機能のために重い依存を増やしすぎない
- 依存先の更新頻度、保守状況、脆弱性リスクを考慮する

## 10. テスト容易性

- テストしにくいコードは設計を見直す
- 副作用のある処理は境界に寄せる
- 振る舞いをテストで説明できるようにする

## 11. 確認スクリプト

- 確認スクリプトは、恒久設定、Secrets、認証情報、ACL、デプロイ設定を暗黙に変更しない
- 実機、外部サービス、本番相当環境に影響する操作は、実行前に対象、影響、復旧方法を明示する
- 環境差分や資格情報は、コード内に埋め込まず、環境変数または明示的な env ファイルから受け取る
- 破壊的操作、再起動、サービス停止、データ削除を行う場合は、明示的なフラグや確認オプションを必須にする
- 失敗時は、原因切り分けに必要なログ、実行コマンド、確認対象、次に見るべき箇所を出力する
- 成功 / 失敗は `[OK]` / `[NG]` など、人間と機械の両方が読める形式で出力する
- 確認後に変更した一時状態は、可能な限り復旧する。復旧できない場合は、残った変更を明示する

## 12. AI エージェントへの指示

- 意味論的な安全性と明確さを重視する
- デフォルト値や暗黙フォールバックを安易にコードへ埋め込まない
- 複雑な分岐や重複処理を見つけたら、簡素化できないかを検討する
- パフォーマンス上の明らかな無駄を見つけたら、説明とともに改善案を提示する
