# UIデザイン共通ベースライン

本書は、UIを設計・変更する際の共通品質基準と、プロジェクト固有の判断を育てる運用を定める。製品のUI仕様は関連SPEC、文書運用は[DOCUMENTATION](./DOCUMENTATION.md)、実装規約は[CODING_GUIDELINE](./CODING_GUIDELINE.md)、作業線と完了判断は既存の正本に従う。適用先のbrand・画面・部品の具体的な方針はREFへ分ける。

## 1. 対象と参照

- 対象UIをプロジェクト索引（既定`docs/REF/REF_ui-guideline_project.md`）のID・path・route・templateから特定する。索引がなければ既存UI文書を先に調べる。
- 一意なら対象と前提を示して進む。「管理画面」などで複数候補が残れば、共通調査を続け、対象依存の変更だけ回答を待つ。
- 共有brand・token・componentの変更は利用先を確認する。対象別の決定を自動で全UIへ広げない。
- 新規IDはlowercase kebab-case。`project`と`brand-`prefixは文書名の予約。既存ID・pathは索引で対応させ、強制改名しない。
- UIがなければ固有文書・ダミー対象は作らない。CLI / Chat等も現行のinteraction designの対象であり、本書の視覚媒体以外を禁止しない。

## 2. 内容と見た目

- 誰が何を理解・判断・操作するかを先に押さえ、情報の優先順位を構図・文字・余白・密度へ表す。
- 新規の方向性は通常2〜3案を目安に、構図・文字・密度等の意味のある違いを表示可能なモックで比較する。採用済み方針内の小変更では案出しを繰り返さない。
- 参考画像がなくてもコードで案を作れる。画像生成・外部デザインツール・特定pluginを必須にしない。
- 実際に近い日本語と情報量、長い名称、空・読込中・失敗など対象に存在する状態を扱う。状態や権限の要件はSPECを参照し、REFへ重複定義しない。
- 特定の配色、書体、カード、角丸、全画面の同じ密度を共通ルールにしない。製品に合う具体案と採用理由を対象側へ残す。
- 案は色だけを変えず、読む順序、主役となる内容、grid、文字の大小・行長、余白と密度、画像の役割を具体化する。日常操作の画面、比較する管理画面、読むメールへ同じ構成を流用しない。
- 採用済みtoken・componentを再利用する。実装値は実装正本を参照し、Markdownへ重複転記しない。実装の作法はCODING_GUIDELINEに従う。

## 3. 品質と媒体

- 対象に合う意味構造・読む順序、識別できる主要操作、状態・入力エラーと回復手段、keyboard / focus、色以外の手掛かり、読める文字・contrastを確認する。
- 数値・規格・platform固有仕様は採用時点の公式一次情報とprojectの要求から決める。全媒体のpixel値を共通化しない。
- Webのアクセシビリティ基準を選ぶ際は[WCAG 2.2](https://www.w3.org/TR/WCAG22/)を参照し、適用level・対象範囲・確認方法をSPEC等に定める。自動検査やスクリーンショットだけで適合を宣言しない。
- webは対象viewport・拡大・keyboard・実際の導線を確認する。スマホ向けWebはviewportの一つであり、別アプリ扱いを強制しない。
- native-mobileは対象OS・platformと実行環境を明記する。HTMLモックでnative動作を確認済みにしない。
- html-emailは対象clientと生成HTMLを明記し、画像・代替文言・リンク・折返し等を確認する。browser previewを実mail client互換性の確認へ読み替えない。送信は別の明示依頼がある場合だけ行う。
- 共有brandは意味・印象・色の役割等を共有する。媒体別の代替表現・token対応には根拠と適用範囲を残す。

## 4. 実画面の確認

- 描画してcaptureを取得し、見た目と実際の操作を確認する。撮影した事実だけで合格としない。
- 対象ID、版、環境、viewport / OS / client、状態、方法、観察した問題、修正・再確認、未確認を現在タスクのWORKへ残す。
- 確認手段がなければ静的検査等を進め、未確認と再開条件を明示する。自動確認は利用者受入や規格への完全適合を意味しない。
- review-onlyではsource・正本文書を変更しない。通常の修正依頼では既存承認の範囲を継続し、軽微な修正ごとに承認を取り直さない。

## 5. 文書と育成

- 共通基準は本書、project / brand / 対象別の採用判断はREF、拘束的な要件はSPEC、比較・途中案・確認結果は現在タスクのWORK。重要な設計判断は必要に応じADRへ接続する。
- SPEC・baselineの必須条件・共有brandと対象方針が矛盾したら、後勝ちで上書きしない。根拠、代替策、例外の範囲、判断者と未反映を残す。
- 観察→試行→採否→適用範囲の判断→正本・実装反映→再確認→統合・修正・廃止、の順で育てる。一画面の好みだけを全UIの規則にしない。
- 既存DESIGN.md等が正本なら索引から参照し、同内容の新しい正本を作らない。雛形は新設時だけ使い、既存文書を再生成しない。
- UI開始時にproject索引・共有brandを最小限作り、対象が1つなら同じ文書内で扱ってよい。必要に応じ`REF_ui-guideline_<target-id>.md`へ分割する。対象は参照brandを明示し、複数brandの暗黙mergeや循環参照を作らない。
- 今のタスクで扱わない気づきは既存capture-inboxへ。kitへ一般化する候補は既存knowledge-feedbackへ。UI専用の別inbox・別feedback経路は作らない。
- UI reviewはsecurity-gateや認可処理の確認を代替しない。必要な技術選定・例外はTECHNOLOGY/ADOPTION、受入・versionは既存の開発・version運用へ接続する。

## 6. 使うスキル

- `project-bootstrap-kit-ui-design`: 初期構想から対象ごとの要求・表示可能な案・採否・固有ガイドラインへ接続する。
- `project-bootstrap-kit-ui-review`: 変更後の実画面・操作と未確認を、対象・媒体に対応させて確認する。
- `project-bootstrap-kit-ui-guideline-maintenance`: 採用判断を正本へ統合し、共有影響・例外・廃止・実装との整合を扱う。

スキルの起動は既存の作業線・承認・受入を置き換えない。通常の自動選択と明示起動は同じ手順を使う。配置先はプロジェクトのAI surfaceに従う。
