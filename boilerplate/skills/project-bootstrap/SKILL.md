# project-bootstrap

## 目的

利用者との対話を通じて、曖昧な発想を検証可能な要求、技術方針、段階計画へ具体化する。

正本は `AGENTS.md`、`docs/DEVELOPMENT_GUIDELINE.md`、`docs/DOCUMENTATION.md`。本 skill は対話と整理を補助する。

## 基本原則

- テンプレートを機械的に埋めず、利用者の発想を広げながら要求を引き出す
- 事実、仮説、利用者が判断した事項、未決事項を区別する
- 一度に全項目を質問せず、1つの論点群ごとに対話、要約、確認を行う
- AI は推奨案を示せるが、未確認の前提を補って仕様や技術構成を確定しない
- 技術候補は、利点だけでなく制約、運用負荷、コスト、変更難易度を比較する
- 不確実性は隠さず、PoC、調査、負荷試験、デザインモックなどの検証タスクへ変換する
- 各文書の内容を利用者が確認してから、次の工程へ進む

## 用語

- 技術実現性検証
  - 採用技術と構成で中核処理を実現できるか確認する
  - Technical PoC に相当する
- 構想・利用体験検証
  - 想定利用者が意図した価値や体験を得られるか確認する
  - Product PoC または Prototype に相当する
- 初期実用提供
  - 実際の利用者が最低限継続利用できる状態を整える
  - MVP に相当するが、本 skill では単独の略語として使用しない

フェーズ番号と開発成熟度は同一ではない。フェーズ1を自動的に PoC または初期実用提供と決めない。

## 対話フロー

### 1. 発想の記録

出力先: `docs/WORK/0.1/idea.md`

確認すること:

- 何をきっかけに思いついたか
- 実際に観察した課題や不便は何か
- 誰が影響を受けているか
- 実現すると何が変わると期待しているか
- 何が事実で、何が仮説か

この段階では機能一覧や技術構成を確定しない。

### 2. 要求とプロダクト定義

出力先: `docs/WORK/0.1/product_definition.md`

対話によって次を具体化する。

- 対象利用者と関係者
- 解決すべき課題
- 提供価値と代替手段
- 初期提供範囲
- 初期提供範囲に含めないもの
- 主要ユースケース
- 機能要求
- 成功条件と受入条件

「欲しい機能」だけでなく、その機能が必要な理由、利用場面、期待する変化を確認する。

### 3. UI / Interaction 構想

出力先: `docs/WORK/0.1/interaction_design.md`

UI / Interaction が必要な場合、GUI / CLI / Chat / API のどれを誰が使うか整理する。

プロダクト価値が GUI や操作体験に依存する場合、API のみでは構想・利用体験検証の完了としない。主要利用者が価値を確認できる簡易 Interface、デザインモック、または仮実装を PoC に含める。

外部公開または外部連携エンドポイントがある場合は、FQDN、環境差分、認証、Cookie、CORS、OAuth redirect、Webhook 署名検証への影響を確認する。

### 4. 技術候補の壁打ち

要求から必要な技術特性を整理し、原則として有力候補を2〜3案提示する。

各候補について次を比較する。

- 要求との適合性
- 実現可能性と既知の制約
- セキュリティ境界
- 性能と拡張性
- 開発・運用負荷
- 無償利用範囲と将来コスト
- ベンダーロックインと変更難易度
- 事前検証の必要性

推奨案を示す場合は理由を説明し、利用者の判断を `product_definition.md` に記録する。

### 5. Technology Profileの選定

出力先:

- `docs/TECHNOLOGY/INDEX.md`
- `docs/TECHNOLOGY/ADOPTION.md`

`init-project.mjs` 実行時にprofileが未指定でも、初期構想を継続してよい。技術候補が確定した時点、または実装着手判定までに次を行う。

1. runtime、integration、storage、framework、toolingに関係するprofile候補を確認する
2. 複数profileが必要な場合は組み合わせて選択する
3. `technology-profile-governance` skillを使い、profile追加のdry-runを提示する
4. 利用者確認後にapplyし、`INDEX.md` と `ADOPTION.md` を確認する
5. profileが存在しない技術は、公式一次情報で制約を確認し、profile追加候補として記録する

### 6. 非機能要件の発見

出力先: `docs/WORK/0.1/product_definition.md` の「セキュリティ」「性能・負荷」「コスト」「運用・可用性・復旧」

すべてを詳細設計するのではなく、プロダクトの成否を左右する事項を特定する。

セキュリティ:

- 守るべきデータ、権限、操作は何か
- 認証、認可、監査が必要な境界はどこか
- 漏えいや不正操作が致命的になる箇所はどこか

性能・負荷:

- 遅いと価値が失われる処理は何か
- 想定利用者数、データ量、実行頻度、ピークはどの程度か
- 負荷試験、PoC、事前計測が必要になる条件は何か

コスト:

- 課金が発生する技術要素と課金単位は何か
- 無償利用範囲を超える条件は何か
- 月額上限、有償化、構成変更、撤退の判断基準は何か

運用・可用性・復旧:

- 必要な監視、ログ、通知は何か
- 許容できる停止時間やデータ損失はどの程度か
- 誰がどのように復旧するか

### 7. 開発成熟度とフェーズ定義

出力先: `docs/WORK/0.1/phase_definition.md`

各フェーズについて次を定義する。

- 技術実現性検証、構想・利用体験検証、初期実用提供のどこを担うか
- そのフェーズで検証する問い
- そのフェーズでは検証しない問い
- 成果物と必要な Interface
- フェーズ完了時点で誰が何を利用できるか
- 次の成熟度へ進む判断条件

PoC が複数フェーズに跨る場合は、各フェーズを `PoC step 1/2` のように位置付け、PoC 全体の完了条件を明記する。

### 8. ロードマップと WBS

出力先:

- `docs/ROADMAP.md`
- `docs/PLAN_PHASE_CURRENT.md`

`docs/WORK/0.1/roadmap.md` で整理した初期構想を `docs/ROADMAP.md` へ反映し、WBS は別の下書き文書を作らず `docs/PLAN_PHASE_CURRENT.md` に直接作成する。

要求、未決事項、技術検証、非機能要件からフェーズと WBS を導く。

必要に応じて次を独立した WBS にする。

- 技術 PoC
- 負荷試験または性能計測
- セキュリティ設計または脅威確認
- コスト試算と課金監視設計
- デザインモックまたは簡易 GUI
- FQDN / 外部エンドポイント設計

### 9. 実装着手判定

`docs/WORK/0.1/implementation_ready_checklist.md` を確認する。

未決事項が残る場合、次のいずれかを明示する。

- 実装前に解決する
- PoC または調査 WBS として扱う
- リスクを受容して後続フェーズへ送る

## 対話時の応答形式

各論点群で、原則として次の順に応答する。

1. 現時点の理解
2. 追加で確認したい質問
3. 選択肢とトレードオフ
4. 推奨案と理由
5. 利用者に判断してほしいこと
6. 確定した内容と未決事項

質問は利用者が判断しやすい数に絞り、回答を受けてから次の論点へ進む。

## 完了条件

- `idea.md` と `product_definition.md` の役割が混同されていない
- 対象利用者、課題、価値、初期提供範囲が明確である
- 技術候補の比較と判断理由が記録されている
- 採用技術に対応するTechnology Profileの追加要否が判断されている
- 選択済みprofileの初期採否と未決事項が `docs/TECHNOLOGY/ADOPTION.md` にある
- クリティカルなセキュリティ、性能、コスト要件が特定されている
- PoC と初期実用提供が区別されている
- フェーズ番号と開発成熟度の対応が明記されている
- UI / Interaction が価値検証に必要な場合、PoC に含まれている
- 未決事項と事前検証が WBS に反映されている
- 実装着手可否を利用者が判断できる
