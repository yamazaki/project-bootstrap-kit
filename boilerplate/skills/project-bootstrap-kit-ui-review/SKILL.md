# UIの実画面と操作を確認する

## 確認範囲

1. 共通baseline、UI索引、関連SPEC、該当brand・対象方針、変更差分を読む。対象ID・path・routeから対象集合を特定する。共有資産の利用先も含める。
2. review-onlyか修正を含む依頼かを区別する。review-onlyではsource・正本文書を変更せず、記録の保存も依頼範囲に従う。対象不明は依存する部分だけ質問する。
3. 対象の確認条件・採用環境を参照する。必要な内容は[媒体別の確認](references/media-checks.md)を読む。全媒体を毎回読み込まない。

## 実際に確かめる

- 起動・描画手段を確認し、対象viewport / 状態でcaptureし、内容・構図・文字・密度・contrast・focus・操作を確認する。採用基準との違いや意図的な差を具体的な箇所で示す。
- screenshot取得と視覚検査、操作試験を区別する。読めない文字、主要操作が見つからない、長い名称や拡大で情報が欠落する等、利用上の問題を優先する。
- 依頼内の修正は実施して再確認する。既存承認内の修正に同じ承認を取り直さない。解消せず同じ結果が続く場合は原因と残課題を記録し、無限に調整しない。
- tool不足でも可能な静的確認は進める。web previewでnative / mail clientを確認済みにしない。送信・deploy・実サービス操作はUI確認から推定しない。
- 認可・security、技術採用、受入等は既存の該当workflowへ接続し、UI合格だけで完了扱いにしない。

## 結果

対象集合、確認版、環境・条件・状態、方法と証跡、問題・根拠、修正と再確認、未確認・次の担当を現在タスクのWORKまたは依頼された報告先へ残す。確認した範囲に限定して結果を述べ、規格・platformへの完全適合を宣言しない。

再発する判断の候補はproject-bootstrap-kit-ui-guideline-maintenanceへ接続する。候補をその場で共有brandや共通baselineへ自動昇格させない。AIの確認結果と利用者レビューの状態を区別する。
