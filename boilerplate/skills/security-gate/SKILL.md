# security-gate

Read `docs/SECURITY_ASSURANCE.md` and the project policy in `docs/SECURITY_ASSURANCE.json`. This skill manages readiness and evidence; Cloudflare performs code audits and OSV scans dependencies. Neither substitutes for the other. It does not approve publication.

## Workflow

1. Identify the trigger, scope, artifact, owner, private external output directory and finite budget. At project start, inspect setup without auditing nonexistent code. Sensitive changes require their relevant boundaries and callers; first public exposure requires a whole-target baseline. Review prior findings and exclusions.
2. Run the read-only plan command in [the command reference](references/commands.md). Explain missing tooling profiles and tools. Add `security-audit-cloudflare` / `security-dependencies-osv` through the existing profile selection and state/plan workflow when needed; never edit bootstrap state by hand. Regenerate the audit plan after accepting profile or policy changes.
3. Present exact source/version, destinations, changes, network/data disclosure, scope, output, budget and rollback. Reuse existing human authorization covering these operations. Otherwise obtain consent for install-and-audit, manual install, or defer. A digest flag is a plan consistency check, not evidence of human consent. Installation-only consent does not authorize a model campaign.
4. After authorization, install only missing standard tools with `install --approve-plan <digest>`. Verify skill recognition, independent agents and sandbox capabilities. Reload/restart if needed and resume with current source/plan checks. Both surfaces receive the same pinned Cloudflare bundle. Existing conflicting skills are preserved.
   When target execution is needed, read [execution environments](references/execution-environments.md) and select a route for the actual coordinating AI and available capabilities. Reuse an accepted project environment first; otherwise consider Codex Cloud for Codex, Claude Code cloud sessions or a dedicated VM/container/CI for Claude. Do not require a Codex account in Claude. A cloud label or built-in shell sandbox does not establish target isolation. Keep unavailable routes as unvalidated and prepare a scoped handoff instead of weakening protections.
5. For Cloudflare, explicitly invoke the installed `security-audit` full workflow, preserving all six phases, independent verification, budget reservations and both upstream validators. Use the selected output root, set metadata `source_ref` to the plan's `sourceFingerprint`, `scope_paths` to the plan's scopes, `target` to its target, and retain the real commit/dirty details as additional metadata. Set `run_status=complete` only after completing Phase 6; record the actual ISO audit completion time in `completed_at`, finite `budget`, observed `agent_invocations`, and `duration_seconds` within the approved policy. Never replace that audit time with import/reimport time. Record `target_execution_performed=false` only for a source-only run. If executing target code, enforce all upstream sandbox controls; a claimed boolean does not provide isolation. Never run live probes or production fixtures. Import the full report with `import-cloudflare`.
6. For OSV, use `run-osv` with reviewed network mode and explicit inputs. For offline operation prepare the DB separately; never silently fall back online. This does not install project dependencies, execute package scripts, fix code or invoke Mantis. The source snapshot must include all dependency inputs required by the release.
7. Run `gate` over both imported results. Inspect missing coverage, unknown severity, unresolved findings, stale source/DB and interruptions. `READY` applies only to the reviewed scope. Do not call a scoped change audit a whole-project release baseline. Review the retained reports and identity of the reviewer; local JSON/checksums cannot prove those facts. Unresolved low/medium findings remain `REVIEW_REQUIRED` until remediated and rescanned or explicitly accepted by the owner with a reason, mitigation and bounded expiry using `accept-findings`. High/critical and unvalidated boundaries cannot be waived by that command.

During ordinary work do not suggest installing Mantis. You may explain that an additional investigation could help, but propose Mantis installation/execution only after an explicit user instruction selecting it. Its absence is not a standard setup error and declining it does not resolve the original risk.

Instructions cannot schedule checks or enforce arbitrary deploy commands. CI protection is a separate integration. Report unavailable capabilities truthfully; do not replace missing independent validation with self-review. Keep raw findings, snippets, credentials and private paths out of public commits and feedback exports.
