# UIガイドラインを育てる

1. baseline、既存索引、関連するbrand・対象方針、SPEC・実装、採否と確認証跡を読む。文書の分類・昇格は既存DOCUMENTATIONとdoc-governanceに従う。
2. 何が観察された事実で、何が提案・好み・採用判断かを分ける。同じ内容の既存規則があれば、不適用・実装不整合・条件の違いを先に調べる。
3. 一時的な調整はWORK、対象固有は対象REF、複数対象に共有すると判断した事項はbrand / 共通pattern、製品の拘束条件はSPECへ接続する。コードの実装規約はCODING_GUIDELINE、技術採否はTECHNOLOGY/ADOPTIONへ。正本の本文を複製しない。
4. 追加・統合・修正・廃止の差分と、適用対象・根拠・例外を示す。共有変更は利用先ごとの影響と必要な実装・再確認を整理する。既存の承認内は進め、未採用の方向や矛盾する上位判断を勝手に確定しない。
5. 採用範囲を正本文書と実装へ反映し、索引・参照・token / componentと整合させる。雛形から既存文書を再生成しない。旧規則は変更理由・後継を追跡できるようにする。
6. 変更した範囲を再確認し、結果・未確認・残作業を現在タスクへ残す。必要な実画面確認はproject-bootstrap-kit-ui-reviewへ接続する。文書を更新しただけで実装や利用者受入を完了にしない。

今のタスクで反映しない候補は既存capture-inboxへ接続する。他projectにも使えるkit改善は既存knowledge-feedbackへ接続し、その固定保存先・匿名化・利用者確認を守る。UI独自のinbox / feedback経路や自動外部提出を作らない。kit baselineの変更はprojectの好みから行わず、kit側の検討事項として扱う。

報告には採否、適用先、変更・根拠、共有影響、実装・確認結果と残作業を含める。候補をすべてルールとして追記せず、既存記述へ統合して読む量を抑える。
